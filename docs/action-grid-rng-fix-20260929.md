# 予測入力導入後の不調：再読込時の乱数リセットを修正

2026-09-29。ユーザー指示により、報酬変更や追加特徴の改善を重ねず、導入差分を検証して修正。

## 再現した不具合

SB3のloadはモデルの再構築でseedを設定し、Python・NumPy・Torchの大域乱数状態を変える。
実機はGPU更新後のモデル読込と各ゲーム終了後の保存確認でloadを呼び、そのモデルで次ゲームへ進んでいた。
保存確認のための読込が探索用乱数まで初期化し、ネットワークの構造に応じて初期化時の乱数消費量も変わる。
そのため予測枝を追加すると、初期出力が同じでも再読込後の探索列が別物となる。
同じ重み・同じ観測で、読込を挟むだけで20操作の抽選列が変わることを再現した。

この再読込経路は予測入力追加以前にも存在した。今回の導入で新たに書いた処理だけのバグではなく、
「既存処理を維持して特徴だけ追加する」という導入検証から漏れた乱数管理の不具合。
実機成績の急落をこれ一つで全て説明できた、とまでは主張しない。

## 切り分け

- 新旧の初期操作確率の最大差は0、価値予測の最大差2.38e-7。初期Torch乱数も一致。
- 予測枝をゼロ出力に固定した32実観測の更新で、既存重みの新旧差はCPU2.98e-8、DirectML1.49e-8。
- CPU/DirectML差は約8.83e-8。枝を無効化した際の既存経路・更新は数値誤差範囲で一致。
- 既存グリッド保持・予測のフレーム対応・実機入力マスク一致も既存テストと受動診断で確認。

予測枝が有効なときに更新が変わること自体は追加機能の作用であり、不具合とは判定しない。
また敵本体への予測対応や死亡罰−1は今回は適用しない。

## 修正

`checkpoint_rng.load_preserving_rng`で読込前の乱数状態を保存し、成功/失敗いずれでも復元。
実機の保存確認・再開・GPU更新結果の読込に適用。
GPU workerへ更新前の乱数状態を渡し、更新後の状態を親へ返す。ミニバッチ順序も毎ゲームseedへ戻さない。
新しい実機checkpointにはcollector_rng_stateを保存し、次回の再開でも復元できるようにした。
ゲーム単位の保存時にreload_rng_verifiedを確認し、状態不一致なら停止する。
追加の乱数情報のI/Oは更新時のみで、毎判断のファイル書込は増やしていない。
